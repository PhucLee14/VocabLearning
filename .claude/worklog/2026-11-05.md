### Decisions
- Codes are 6 digits, valid for 10 minutes and single use. Each code is bound to the user and the action (`set_password`, `delete_account`). A code allows at most 5 attempts, and a new one can be sent at most once a minute.
  - Codes are stored as a salted SHA-256 in `auth_tokens`: type `ACTION_CONFIRM`, new columns `action` and `attempts`.
  - Sending a new code invalidates the unused ones for that action. If the email fails, the token is deleted and the request returns 503.
- Only accounts **without a password** use codes. Accounts with a password keep confirming with the password (403 when it is wrong).
- Missing or wrong code → 403 (same as a wrong password); the frontend shows "Wrong or expired code".
- **CSRF:** one Express middleware runs before every route. It refuses a write request in three cases:
  - `Sec-Fetch-Site: cross-site` → 403;
  - an `Origin` that is not in `FRONTEND_URL`, `null` included → 403;
  - a body that is not JSON → 415.

  The same middleware adds nosniff, `X-Frame-Options: DENY`, Referrer-Policy and COOP.
- **Sliding sessions:** Server Component fetches send `x-vocab-ssr: 1` and never extend the session. Browser requests through the `/api` rewrite do extend it, and the new `SessionKeepAlive` component pings `GET /api/auth/session` at most every 12 hours. Sessions also have a 90-day absolute limit; the limit applies to the expiry when a session is extended and when it is resolved.
- **Double ratings:** optimistic concurrency on `user_cards` (`updateMany … where reps = <read value>`). A lost race returns 409, and the client ignores it.
- **Notes:** `@@unique([userId, wordId])` plus upsert. The migration first deletes duplicates, keeping the newest note.
- **Progress:** the weekly recall is aggregated in SQL (`date_trunc('week', … AT TIME ZONE tz)`).
