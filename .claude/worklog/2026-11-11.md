### Decisions
- **Links, not codes**, for verification and reset.
  - Each link carries a random 256-bit token in the URL **fragment** (`/<locale>/reset-password#token=…`), so the token never reaches a server log or a Referer header. The page reads it, removes it from the address bar, and POSTs it.
  - Only the token's SHA-256 is stored, in `auth_tokens` (types `EMAIL_VERIFY` and `PASSWORD_RESET`, which already existed).
  - Verification links are valid for 24 h, reset links for 30 min; both work once. A new link replaces the unused ones of the same kind.
- **Verification is soft**: nothing is blocked for unverified accounts yet. Dashboard and Settings show a notice with "Send link again" (at most 1 a minute and 5 an hour).
  - The verify page asks for a click instead of verifying on load. Mail scanners can open links, and a verified email decides whether Google sign-in keeps the existing password (pre-hijack protection in `signInWithGoogle`).
- **Sign-up** sends the first verification link, but a mail failure never fails the sign-up; the failure is only logged.
- **Forgot password** always answers 204, so it doesn't reveal which emails have accounts.
  - A sign-up with an existing email still answers 409, so that endpoint can still reveal accounts; accepted.
  - Timing can also differ when an email is actually sent.
- **Reset password**:
  - sets the password, marks the email verified (the link proves control of it) and revokes every session and every other reset link;
  - works for Google-only accounts too, which then also get a password;
  - a normal password change now also voids pending reset links.
- **Rate limiting**:
  - stored in a Postgres table `rate_limits` (fixed window, one atomic `INSERT … ON CONFLICT` per rule), so it needs no new service and holds across serverless instances;
  - keys are `<bucket>:<sha256(id)>`, so raw IPs and emails are never stored;
  - expired rows are deleted on about 1% of hits.

  | Where | Limit |
  |---|---|
  | Login | 10 per 15 min per IP + email; 50 per hour per email; 100 per 15 min per IP |
  | Register | 20 per hour per IP |
  | Forgot password | 20 per hour per IP (429); 3 emails per hour per address (silent) |
  | Link submits | 60 per 15 min per IP |
  | `/me/password`, `/me/delete` | 10 per 15 min per user |
  | `/me/confirm-code` | 10 sends per hour per user, on top of 1 per minute |
- **Client IP**: Vercel documents that rewrites to an external origin pass `x-forwarded-for`, but it also overwrites that header when a proxy sits in front of it. Behind the frontend's `/api` rewrite, the backend may therefore see a Vercel address instead of the visitor's.
  - Per-IP limits are generous for that reason; per-email and per-account limits do the real work.
  - `/api/health/db` (behind `CRON_SECRET`) now reports the `ip` it sees, so this can be checked in production.
