### Decisions

### Work done
- Read the skill before installing it:
  - `check.py` uses only the Python standard library;
  - it sends only GET/HEAD/OPTIONS requests, and only to the target URLs (DELETE appears only as a CORS preflight header);
  - no shell calls, no file writes;
  - the checklist contains no outbound links or odd instructions.
- Ran the live scan against production: `https://godee.vercel.app` with `--api https://vocab-learning-eight.vercel.app/api/health`, 138 requests.
  - Result: **18 passed, 6 failed, 3 warnings**.
  - Passed: no exposed `.env`/`.git`/dumps, no directory listing, no public source maps, CORS is closed to foreign origins, error pages don't leak details, no debug/docs endpoints, HSTS, HTTP → HTTPS, X-Frame-Options, nosniff, Referrer-Policy.
  - All 6 failures have one cause: the frontend CSP holds only `frame-ancestors 'none'`. Missing: `default-src`, `script-src`, `object-src`, `base-uri`, `form-action`, and the fetch directives.
  - Warnings:
    - the `NEXT_LOCALE` cookie has no `Secure` flag (not a session cookie);
    - `_next/static` files lack nosniff and HSTS (served by Vercel's CDN, not by `headers()`).

### Notes for the CSP fix
- `frontend/node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md` says nonce-based CSP needs dynamic rendering and is incompatible with PPR. That rules it out here: pages are static, and the theme script is inline.
- Options:
  - a static CSP in `next.config.ts` with `script-src 'self' 'unsafe-inline'` plus all the other directives;
  - or the experimental SRI (`experimental.sri`) with hashes, which keeps static generation and allows a strict `script-src`.
  - Either way, roll it out as `Content-Security-Policy-Report-Only` first.

### Next

## Session 2: full CSP (option 2)

### Request
- Add `security/` to `.gitignore`; explain CSP; then implement "option 2": a static CSP with every directive, keeping `'unsafe-inline'` in `script-src`.

### Work done
- `.gitignore`: `/security/`.
- `frontend/next.config.ts`: the CSP is now:

  ```
  default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
  img-src 'self' data: blob:; font-src 'self'; media-src 'self' https://api.dictionaryapi.dev;
  connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
  ```

  `'unsafe-eval'` is added in dev only.
  - External sources were checked first: word audio is the only one (all 12,982 `audio_url`s in the word data are on `api.dictionaryapi.dev`). There are no external images, Google sign-in is a link rather than a form, and fonts are self-hosted by `next/font`.
- Enforced directly instead of Report-Only, because a real-browser check found no violations (see Verification).
- `.claude/CLAUDE.md`: a CSP note (add new external hosts to the policy).

### Problems
- `upgrade-insecure-requests` upgraded redirects on `next start` at http://localhost to https (`ERR_SSL_PROTOCOL_ERROR`). Removed: HSTS already covers production and every URL is relative or https.
- **Word audio is broken, independently of CSP.**
  - `api.dictionaryapi.dev/media/...mp3` answers **403 with an HTML page** (with `x-ratelimit-reset`), both from curl and from a browser on the current production site, which still has the old CSP.
  - The browser blocks it (ORB / "Format error"). `AudioButton` falls back to speechSynthesis on a play error, so users hear the browser voice.
  - It may be a rate limit tied to this machine's IP (the enrich runs called that API a lot), or a lasting block. Long-term fix: self-host audio (Phase 3c, Kokoro → Blob/R2).
